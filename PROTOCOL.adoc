= Training protocol

This file documents how `skills.yaml`, `practice/`, and `tests/` work together, and how `cmd/reportgen` turns them into `README.md`. Any AI agent picking up work in this repo should read this first as it defines the contract, not just a convention.

For the reasoning behind these rules, see `RATIONALE.adoc`. This file stays action-oriented on purpose.

== The pieces

=== Skill registry

`skills.yaml` is the flat skill registry, and the source of truth for what's being tracked:

* a `levels` list (display order)
* a `categories` map (pure display metadata, see "Skills are flat" below)
* a `skills` list where every entry has a `slug`, `label`, `rubric`, `level`, and optionally `categories`

Every skill is independently scoreable, computed from `tests/*/` on demand. Nothing in `skills.yaml` is ever hand-edited to reflect a result.

`rubric` is a tiered pass bar: up to three one-sentence bars (`orange`, `yellow`, `green`), graded top-down. `green` is required. `orange` and `yellow` are optional and fill from the bottom. A skill can define `green` alone, `orange` and `green`, or all three, but never `yellow` without `orange`.

=== The report generator

`cmd/reportgen` is a small Go program (`go run ./cmd/reportgen`) that reads `skills.yaml` and every test under `tests/` and renders a completion report into `README.md`, the repo's actual front page.

`README.md` starts out as the traditional onboarding content (what this repo is, how to use it, quick start). The report generator overwrites it with the live report on its first run, and every run after.

The report renders natively on GitHub. Every skill's row shows a status icon (⚪🔴🟠🟡🟢⭐) reflecting its current position on the ladder (see "From test results to skill state" below), and links to the tests that produced it.

`README.md` is generated, not maintained by hand. Re-run `go run ./cmd/reportgen` after logging a new attempt. Commit it to version control alongside `skills.yaml` and `tests/`.

The report's footer links back to the original repository. Update it by hand if the template ever moves.

=== Practice folders

The `practice/` folder holds self-directed practice projects, maintained by the user. The agent does not create or grade content here unless explicitly asked.

=== Test folders

`tests/<test_id>/` holds one folder per assessment the agent has administered or prepared. A test is not tied 1:1 to a skill: one test is designed to assess one or more skills at once, and its solution can incidentally demonstrate more.

`<test_id>` is a short descriptive slug for the assessment itself (e.g. `spot_the_bug`, `fizzbuzz`), not a skill name.

Each test folder holds two files with different lifecycles:

`metadata.yaml`:: the read-only spec: what the test checks for and which skills it was designed to evaluate. Don't edit it once the test has attempts recorded against it; design a new test instead of changing what an existing one measures.
`scorecard.yaml`:: the mutable results: the test's own `test_id` (checked against the folder name), whether it's been passed, anything incidentally demonstrated, and the full attempt history.

The latest attempt's submission, for file-based tests, lives at `tests/<test_id>/deliverables/`.

== Skills are flat

Every skill in `skills.yaml` is independently scoreable and stands on its own.

Slugs are a single flat namespace matched by plain string equality, so generic names (`os`, `time`, `comments`) are collision-prone. Prefer specific slugs (`os_package`, `idiomatic_comments`) over bare generic ones.

A skill represents one discrete, nameable command or capability. Split into separate skills when two capabilities are genuinely different commands. Tier within one skill (`orange`/`yellow`/`green`) for a depth/breadth gradient on the *same* command. Leave a skill single-tier (`green` only) for a holistic spectrum with no natural stopping point short of full sophistication.

=== Categories

`categories` are purely a display column. A category is defined once in `skills.yaml`'s top-level `categories` map and referenced by slug from a skill's own `categories` list, but it carries no score of its own and is never itself a slug a scorecard can reference (`cmd/reportgen` fails validation if one tries to).

A skill can belong to zero, one, or several categories. `level` is *not* a category: it's its own required field, because every skill needs exactly one and it drives `README.md`'s top-level sections.

== Test folder naming

Slug the test's own task or topic, not a skill name: lowercase, underscores for spaces. `tests/a_test_identifier/` is the template/example folder. You can copy its shape (`metadata.yaml`, `scorecard.yaml`, `deliverables/`, a spec file) when creating a new test, then rename it.

== Grading flow

The agent picks the grading mode per test, based on what the skill actually is:

File-based:: for skills that produce artefacts (write functions, write tests, work with packages, design services). The agent puts a task spec into the test folder (e.g. `todo.adoc`), the user writes their solution into `deliverables/`, the agent reviews/runs it and records the result.
Conversational:: for conceptual/understanding skills (syntax, memory model, GC, basic concurrency concepts). The agent quizzes the user live in chat; nothing is persisted in the folder except the logged outcome.
Externally verified:: for skills whose truth lives outside any conversation or file (an open-source contribution, a Go-language contribution). The agent asks for a URL, fetches and checks it (confirms authorship, confirms it's actually merged/accepted, not just opened), and logs a single attempt whose `notes` state exactly what was checked. These attempts are always logged at `tier: green`.

The agent states which mode it's using before starting a given test.

=== Sizing a test

Keep Beginner tests narrowly scoped to one or two closely related skills. From Intermediate up, a test covering several related skills at once is fine and preferred.

=== Skeletons for file-based tests

For Beginner tests, and narrowly-scoped Intermediate tests (a single function/algorithm to implement), the agent may provide an interview-style skeleton: a function signature to fill in plus a visible test file.

For tests where the scaffolding itself *is* the skill being assessed ("can work with packages," "design and implement services from scratch," and similar Proficient+ items), the agent does not provide a skeleton.

=== Incidental signals

The agent isn't limited to the skills a test was designed for. If a conversation or a test attempt shows clear, substantive evidence for a skill that wasn't the target, the agent records it under `demonstrated` in the relevant scorecard. A skill merely being mentioned in passing doesn't count, and neither does gratuitous or forced use.

`demonstrated` evidence is held to a higher bar than `assesses` evidence before it counts toward a skill's state at all: see "From test results to skill state" below.

== Grading rubric

An attempt grades every skill it touches separately, under `tiers`: one `skill`/`tier` pair per skill this sitting actually assessed or demonstrated. A test that covers several skills at once (see "Sizing a test" above) can clear a different bar for each. There is no single tier for the whole attempt.

Each `tier` (`fail`/`orange`/`yellow`/`green`) is graded directly against that skill's own tiered `rubric` in `skills.yaml`, top-down: does this attempt clear the skill's `green` bar? If not, `yellow`? If not, `orange`? If it clears none of the bars the skill defines, it's `fail`. A tier must be one the skill's rubric actually defines. `tier: orange` against a skill with no `orange` bar is a validation error, not a silent no-op.

`notes` is required unless every skill in `tiers` is a clean `green` pass. If anything graded lower needs explaining, `notes` is where it goes: what was tried, what almost worked, what a fail actually revealed, or, for externally-verified skills, the checked URL and what it confirmed. This is enforced by the report generator (`validateAttempt`), not just convention.

== Schemas

.`metadata.yaml`
[source,yaml]
----
# metadata.yaml -- read-only, see "Test folders" above
name: <test_id>
summary: >
  <what this test is checking for, one or two sentences>
assesses:
  - <skill_slug>       # skills this test was designed to evaluate
----

.`scorecard.yaml`
[source,yaml]
----
# scorecard.yaml -- mutable results
test_id: <test_id>      # must match the folder name and metadata.yaml's name
passed: true | false    # did the *test itself* clear its own bar
demonstrated:
  - <skill_slug>         # skills incidentally shown, not the test's target
attempts:
  - date: YYYY-MM-DDTHH:MM  # minute precision -- see "From test results to skill state"
    tiers:
      - skill: <skill_slug>  # must be in this test's assesses/demonstrated
        tier: fail | orange | yellow | green  # must be a tier the skill's rubric defines
    notes: "short note"   # required unless every tier above is green -- see "Grading rubric"
----

`passed` means at least one attempt in this test's history cleared at least the lowest tier some skill defines (`tier` other than `fail`, for at least one entry in `tiers`). Every slug in `assesses`/`demonstrated` must be a real skill slug from `skills.yaml`, and every `tiers[].skill` must be one of them. The report generator fails validation if any of that doesn't hold.

== From test results to skill state

Each skill sits on a six-position ladder: untested (⚪), then red (🔴), orange (🟠), yellow (🟡), green (🟢), and mastered (⭐). The ladder is a state machine, walked by folding every attempt that graded the skill (its own entry under that attempt's `tiers`, see "Grading rubric"), across every test, in `date` order, which is why `date` carries minute precision: two attempts on different tests can land on the same calendar date, and only the timestamp keeps their real order intact.

1. A *pass* (any tier other than `fail`) climbs to the rung matching the tier it cleared, but never climbs *down*.
2. A *fail* steps the skill down exactly one rung: green to yellow, orange to red. A skill that has never been proven doesn't turn red on a failed attempt. Red is reachable only by falling from orange. Once at red, further fails hold the floor.
3. *Mastered* is earned by at least three green-tier passes, uninterrupted by any fail. The pass that reached green in the first place counts towards it. A fail at any point resets that count to zero, even from green or master itself. The count is a single tunable constant (`greensForMaster` in `cmd/reportgen/confidence.go`).
4. `demonstrated` evidence only counts if the pass was `tier: green`. An orange- or yellow-tier incidental touch is invisible to the ladder, neither a climb nor a fail.
5. Categories never get their own state. The report shows a skill's categories as plain text, not a rollup.
6. Nothing in `skills.yaml` needs manual editing to reflect a skill's current rung. Re-running `go run ./cmd/reportgen` after logging an attempt is enough.

== Regenerating README.md

`go run ./cmd/reportgen` from the repo root (flags: `--skills`, `--tests`, `--out`, all defaulted sensibly). Requires `go mod tidy` once, since the generator depends on `gopkg.in/yaml.v3`. You can do this inside the devcontainer, which has the Go toolchain, if your host does not.
